# Architecture

The app is a React and TypeScript application built with Vite and packaged as a standalone Tauri 2 desktop application. Its UI runs locally in the native window; it does not require a web server or remote service after installation. Calculation functions are plain TypeScript modules and do not depend on UI code. Skill data is stored separately from calculations and carries source/version metadata.

The current vertical slice is Woodcutting. `src/calculator.ts` owns deterministic XP/action/time arithmetic; `src/data/woodcutting.ts` holds the reference rows; `src/App.tsx` provides the calculator interface. Save bytes are decoded by read-only Tauri commands in `src-tauri/src/save_decoder.rs`; the UI passes local file bytes, pasted Base64, or a filename inside a user-selected save directory. The directory/filename and optional five-minute auto-refresh preference are kept in localStorage. Explicitly saved character profiles are validated with Zod and stored in IndexedDB by UUID; raw compressed saves are not persisted.

The save decoder also returns supported toolbelt, shop, Astrology, and Mastery Guild fields. Unknown components remain opaque. Save parsing stays local and read-only.

## Adding a skill to resource planning

- **Recipe data** lives in `src/data/resource-recipes.ts` and skill-specific data modules. A recipe uses the same `SkillAction` input and output rows as the calculator, with a skill, source link, and optional prerequisite note. Use the game item IDs used by the bank decoder, positive whole quantities per completed batch, and a full-batch time in seconds.
- **Character effects** are resolved before planning. The calculator and recipe adapter both use `resolveWoodcuttingRates` for supported XP, timing, and output effects. The planner receives guaranteed yields and costs plus estimated active time. A new skill can supply its own rates through the recipe adapter without changing the dependency algorithm.
- **Dependency and inventory logic** lives in `src/resource-planner.ts` and has no React or save-format dependency. It plans against a virtual inventory, allocates owned stock once, rounds up to complete batches, and reuses earlier surplus and co-products. It returns a dependency tree, a flattened checklist, and active time and XP by skill. Recursion stops at unsupported items and dependency cycles. Both views use the same inventory merge function and manual overrides.
- **Source selection** prefers recipes whose current level and known prerequisites are met, then prefers non-shop and guaranteed routes before comparing direct seconds per item. Users can select a different source. The model follows ingredient order and does not search for a globally optimal chain. It flags external supply and prerequisites and reports active time for the modeled steps only.
- **Other acquisition methods** use the same recipe contract. Mining supplies a guaranteed batch and an expected duration with a hit cap. A chance-based recipe names one random batch output and its success probability. The opt-in mode budgets complete attempts from the mean time to the required successes, and conditional output supplies only that branch. Shop recipes can consume item inputs and currencies. Costs are summed in integer units and compared with the imported wallet using BigInt.

The catalog includes supported Woodcutting, Mining, and Firemaking actions and selected Crafting, Fletching, Smithing, and shop recipes. Copper and Iron Ore use base Mining rates. Random yields are opt-in and material budgets exclude preservation. Feathers remain an external input when unavailable in inventory. Temporary Woodcutting effects remain deferred.
